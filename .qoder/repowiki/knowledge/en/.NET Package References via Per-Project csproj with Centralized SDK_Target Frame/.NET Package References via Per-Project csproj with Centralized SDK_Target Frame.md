## What system/approach is used

This .NET 8 solution manages third-party dependencies through the standard NuGet `PackageReference` mechanism declared inside each project's `.csproj` file. There is no centralized package version store (no `Directory.Packages.props`, no `packages.config`, no global.json package lock). Instead, every dependency is pinned to an explicit version directly in the project that consumes it. The shared build target framework (`net8.0`) and compiler options are centralized in a root `Directory.Build.props` so all projects inherit consistent settings without duplicating them.

## Key files and packages

- **`Ecommerce.sln`** — Solution manifest listing the four source projects (`Ecommerce.Domain`, `Ecommerce.Application`, `Ecommerce.Infrastructure`, `Ecommerce.Api`) and three test projects; project-to-project references define the layering.
- **`Directory.Build.props`** — Root MSBuild props setting `<TargetFramework>net8.0</TargetFramework>`, `<Nullable>enable</Nullable>`, `<ImplicitUsings>enable</ImplicitUsings>`, `<LangVersion>latest</LangVersion>` for every project under the repo.
- **`src/Ecommerce.Domain/Ecommerce.Domain.csproj`** — Domain project has no `PackageReference`s; it depends only on other domain code, keeping the core free of external libraries.
- **`src/Ecommerce.Application/Ecommerce.Application.csproj`** — Declares AutoMapper (`12.0.1`), FluentValidation (`12.1.1`), and EF Core (`8.0.0`).
- **`src/Ecommerce.Infrastructure/Ecommerce.Infrastructure.csproj`** — Declares JWT Bearer (`8.0.0`), ASP.NET Identity EF (`8.0.0`), EF Core + SQL Server provider (`8.0.0`), configuration abstractions (`8.0.0`), and `System.IdentityModel.Tokens.Jwt` (`8.22.0`).
- **`src/Ecommerce.Api/Ecommerce.Api.csproj`** — Web host adds FluentValidation.AspNetCore (`11.3.1`), Swashbuckle/OpenAPI (`7.0.0`), JWT Bearer (`8.0.0`), Identity EF (`8.0.0`), and EF Core Design (`8.0.0`) marked with `PrivateAssets=all` and scoped to build-time assets.
- **`tests/Ecommerce.Application.Tests/Ecommerce.Application.Tests.csproj`** and **`tests/Ecommerce.IntegrationTests/Ecommerce.IntegrationTests.csproj`** — Both use xUnit (`2.9.3`), Microsoft.NET.Test.Sdk (`18.9.0`), xunit.runner.visualstudio (`4.0.0`), and `Microsoft.EntityFrameworkCore.InMemory` (`8.0.0`) for isolated testing.

## Architecture and conventions

- **Layered dependency declaration**: Each layer declares only the packages it needs. The Domain layer stays dependency-free (no `PackageReference`), Application pulls in mapping/validation/EF Core interfaces, Infrastructure brings in concrete EF Core/SQL Server/JWT implementations, and Api composes presentation concerns (Swagger, FluentValidation integration).
- **Project-to-project references enforce layer boundaries**: The API references Application + Infrastructure; Infrastructure references Application + Domain; Application references Domain. This mirrors the Clean Architecture rule that lower layers never depend on higher ones.
- **Build-time-only packages are gated**: Packages like `Microsoft.EntityFrameworkCore.Design` and `xunit.runner.visualstudio` are declared with `<IncludeAssets>runtime; build; native; contentfiles; analyzers; buildtransitive</IncludeAssets>` plus `<PrivateAssets>all</PrivateAssets>`, ensuring they participate in compilation but do not flow as runtime dependencies into consuming projects.
- **No vendoring or private registry**: There is no `NuGet.config`, no `packages/` folder, no `global.json` package redirects, and no local/private feed configured. All packages resolve from the default NuGet.org feed.
- **No lockfile committed**: No `packages.lock.json` appears in the repository, so deterministic builds rely on exact version pins in each `.csproj` rather than a shared lockfile.

## Conventions and constraints

- Every third-party library is pinned to an explicit semantic version string inside the consuming `.csproj`; there is no wildcard or version range usage observed.
- Target framework is enforced centrally via `Directory.Build.props` (`net8.0`); adding a new project automatically inherits this constraint.
- Test projects are identified by `<IsTestProject>true</IsTestProject>` and consistently reference the same test stack (xUnit + Test.Sdk + Visual Studio runner).
- Cross-cutting infrastructure concerns (JWT, Identity, EF Core) are co-located in the Infrastructure project, while the Api project only wires them up — this keeps dependency ownership clear per layer.
- Because versions are duplicated across projects (e.g., EF Core `8.0.0` appears in both Application and Infrastructure), there is no single source of truth for package versions; updating a shared package requires editing every project that references it.
