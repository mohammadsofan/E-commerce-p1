## What system/approach is used

The repository uses the standard .NET `Microsoft.Extensions.Configuration` pipeline with JSON configuration files. The API project (`Ecommerce.Api`) is an ASP.NET Core web application that relies on `WebApplication.CreateBuilder(args)` to build a default configuration source chain (environment variables, command-line args, `appsettings.json`, `appsettings.{Environment}.json`). There are no custom configuration loaders, YAML/TOML/`.env` parsers, or feature-flag frameworks — all runtime settings flow through `IConfiguration`.

## Key files and packages

- `src/Ecommerce.Api/Program.cs` — entry point; builds the host, reads JWT settings via `builder.Configuration["Jwt:Key"]` and `builder.Configuration["Jwt:Issuer"]`, passes `builder.Configuration` into infrastructure registration, and gates Identity/JWT setup in a try/catch so the app can run without those packages installed locally.
- `src/Ecommerce.Api/appsettings.Development.json` — development-only configuration containing `Logging`, `Jwt` (`Key`, `Issuer`), and `ConnectionStrings.DefaultConnection` pointing at a local SQL Server instance.
- `src/Ecommerce.Infrastructure/DependencyInjection.cs` — extension method `AddInfrastructure(IConfiguration)` that reads `DefaultConnection` via `configuration.GetConnectionString("DefaultConnection")` and registers `ApplicationDbContext` with `UseSqlServer(conn)`. This is the single place where the connection string name convention is enforced.
- `src/Ecommerce.Infrastructure/Auth/JwtTokenService.cs` — consumes `IConfiguration` directly for `Jwt:Key` and `Jwt:Issuer` with fallback defaults (`"default_dev_key_change_me"`, `"ecommerce"`), demonstrating per-service configuration access rather than strongly-typed options classes.
- Test projects reference `Microsoft.EntityFrameworkCore.InMemory` and use `DbContextOptionsBuilder<ApplicationDbContext>().UseInMemoryDatabase(...)` to bypass file-based config during tests; they construct contexts inline rather than reading from `appsettings`.

## Architecture and conventions

1. **Single configuration consumer surface**: `Program.cs` is the only place that constructs the host and wires configuration into DI. All other layers obtain settings by injecting `IConfiguration` (e.g., `JwtTokenService`) or via `GetConnectionString` inside infrastructure registration.
2. **Environment-scoped JSON files**: Only `appsettings.Development.json` exists under `Ecommerce.Api`; production would rely on environment variables or a separate `appsettings.Production.json` not present in the repo. No base `appsettings.json` is checked in.
3. **Connection string naming convention**: The infrastructure layer expects a connection string named exactly `DefaultConnection` (see comment in `DependencyInjection.cs`: "Example connection string name: 'DefaultConnection'").
4. **Fallback defaults for secrets**: Both `Program.cs` and `JwtTokenService.cs` provide hardcoded fallback values when `Jwt:Key` / `Jwt:Issuer` are missing, allowing the API to start even without configuration. This is a convenience for development but means secrets are not strictly enforced at startup.
5. **Optional package bootstrapping**: Registration of Identity/JWT, FluentValidation validators, AutoMapper profiles, and EF provider is wrapped in try/catch blocks so missing NuGet packages do not prevent the app from building/running locally. The same pattern appears in `DependencyInjection.cs` and `Program.cs`.
6. **Tests avoid external config**: Integration and application tests create `ApplicationDbContext` instances programmatically with `UseInMemoryDatabase(...)`, never reading `DefaultConnection` from configuration. This isolates test execution from any database configuration.

## Conventions and constraints

- **JWT settings shape**: The configuration must expose a `Jwt` section with `Key` and `Issuer` keys. If absent, both locations fall back to hardcoded strings, so the app still runs but tokens will be signed with a dev key.
- **Connection string name**: The EF registration hardcodes the lookup name `DefaultConnection`. Changing this name requires updating `DependencyInjection.cs`.
- **No typed options**: The codebase does not define `IOptions<T>`-style strongly-typed configuration classes; settings are read as flat string keys via `configuration[...]` or `GetConnectionString`.
- **No centralized secrets management**: Secrets (JWT signing key, DB connection string) live in `appsettings.Development.json` and are intended to be overridden via environment variables or deployment-time configuration; there is no Azure Key Vault, AWS Secrets Manager, or user-secrets usage in the checked-in code.
- **Development-only logging level**: Logging verbosity is configured only in `appsettings.Development.json` (`Default: Debug`, `Microsoft: Warning`). Production logging levels are not defined in the repo.
